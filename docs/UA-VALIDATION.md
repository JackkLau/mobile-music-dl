# UA 真机验证记录

日期：2026-10-28（Asia/Hong_Kong）。来源：本项目用户在原会话提供的日志与最终真机测试结论。本文件保留历史证据；没有将其记为本次恢复版本的新一轮设备测试。

## 历史用户反馈（不是本轮复测）

| 阶段 | 桌面 UA | 移动 UA |
|---|---|---|
| 视频信息和音轨地址解析 | 可正常解析 | 可正常解析 |
| 音频下载 | 可正常下载 | 被拒绝，HTTP 403 |

根据反馈，普通模式默认使用桌面音频 UA，解析默认也使用桌面 UA。CDN 节点同时变化，尚不能证明下载 UA 是唯一根因。开发者模式可单独覆盖两阶段 UA；关闭后忽略并清除测试配置。

## 排查经过与边界

1. 初期已获得独立音轨地址，但 `mirrorbd`、`mirrorbdb` 等多个音频 CDN 返回 403，重新取流后仍拒绝。
2. 修复视频页 Referer、加入 Origin 与初始 `Range: bytes=0-` 后，用户日志仍为 403。不能将这些请求格式修正误写成已解决问题。
3. 解析与下载改成桌面 UA 后，用户提供 `http=206 profile=web_media range=open ua=desktop` 日志，域名包括 `upos-sz-mirrorhw.bilivideo.com`、`upos-sz-estgoss.bilivideo.com`。
4. 此时 UA 与 CDN 节点同时变化，单凭该日志不能区分两者影响。
5. 增加分别切换解析/音频 UA 和同地址对照后，用户明确确认：“需要使用桌面端 ua 才能正常下载，解析使用桌面端或者移动端都可以解析。”因此默认行为落实为桌面音频 UA。

原会话未附最终完整同地址对照日志，因此保留结论来源为“用户真机确认”，不虚构每组请求、账号、网络、服务器内部风控规则或唯一机制。不能据此推断所有移动设备被禁止下载，也未验证视频流下载。

## 本次重建后的复测

1. 同一设备、网络和访问模式下，解析同一分 P。
2. 开启开发者模式，解析 UA 为桌面，运行同地址对照；再用移动解析 UA 重复一次。
3. 比较每次相同 `request`、`url_id` 下的桌面/移动音频 UA、HTTP 状态及样本有效性。
4. 默认桌面音频 UA 在应用内下载一首尚未保存的音频；确认出现 `saved` 及可离线播放。`local_hit` 不证明新网络请求成功。
5. 关闭调试模式，确认入口隐藏；新请求恢复桌面 UA，日志不再输出。重启与 release 构建也应忽略旧覆盖配置。

重新构建版本的 UI、完整下载、M4A 保存与真机登录仍需复测，不能沿用旧版本验收结果。

## 2026-10-28～29 Mac 新样本证据

本轮对交接的桌面、移动和 b23.tv 链接使用共用 Kotlin 工具，每类链接分别用两种解析 UA 取流。六组对照内部的 request、url_id 和 CDN host 保持一致；桌面下载 UA 均返回 206，1024 字节样本通过 MP4 文件头检查，移动下载 UA 均返回 403。原始脱敏日志及设备结果见 [HANDOFF-VERIFICATION.md](HANDOFF-VERIFICATION.md)。这是这些地址的同地址样本证据，不能回推此前所有 403 的唯一根因；仍不能替代完整下载、M4A 保存和离线播放。
